# Tabby 智能上传插件 · 开发调试手册

## 一、项目概况

| 项 | 内容 |
|---|---|
| 插件名 | `tabby-smart-upload`（智能上传） |
| 目录 | `C:\dev\code\tabby-upload-plugin`（WSL: `/mnt/c/dev/code/tabby-upload-plugin`） |
| 技术栈 | TypeScript 4.9 + Angular 15（宿主共享运行时）+ webpack 5 + ts-loader |
| 目标宿主 | Tabby 最新版（Windows 宿主机安装） |

架构：Tabby 插件 = 一个默认导出 NgModule 的 npm 包（`tabby-plugin` keyword），
运行时 `tabby-*` / `@angular` / `@ng-bootstrap` / `rxjs` 全部 external、与宿主共享
同一模块实例（webpack externals），插件目录被加进 Node 模块搜索路径。

## 二、构建环境

- WSL 便携 Node：`/tmp/opencode/node/bin`（Node v22.17.0，/tmp 重启即失，按上法重装：
  `curl -fsSL -o /tmp/opencode/node.tar.xz https://registry.npmmirror.com/-/binary/node/v22.17.0/node-v22.17.0-linux-x64.tar.xz` 解压即可）
- npm 源：`--registry=https://registry.npmmirror.com`（GitHub/npm 官方源在 WSL 直连不通，npmmirror 直连可用）
- Windows 宿主机也有 Node：`C:\nvm4w\nodejs\node.exe`（v24.16.0），可在 Windows 侧自行构建

```bash
cd /mnt/c/dev/code/tabby-upload-plugin
export PATH=/tmp/opencode/node/bin:$PATH
npm install --registry=https://registry.npmmirror.com   # 首次
npm run build      # 产出 dist/index.js
npm run watch      # 监听重建
```

## 三、Windows 宿主机调试方法（核心）

Tabby 安装在 Windows 宿主机会从 `%APPDATA%\tabby\plugins\node_modules\tabby-*` 扫描加载插件。

### 方式 A：目录联接（推荐，日常开发）

项目根目录已带 `use-in-tabby.ps1`，在项目目录的 PowerShell 里执行：

```powershell
.\use-in-tabby.ps1              # 构建 + 建 Junction（插件目录 → 项目根）
.\use-in-tabby.ps1 -NoBuild     # 跳过构建只部署
.\use-in-tabby.ps1 -RestartTabby  # 部署后顺便重启 Tabby
```

之后 `npm run watch` 每次重建产物，**重启 Tabby（或重开窗口）**即加载新版。
Junction 无需管理员权限；卸载插件 = 删除 `%APPDATA%\tabby\plugins\node_modules\tabby-smart-upload` 链接。

### 方式 B：手工拷贝（不建链接）

```powershell
npm run build
$dst = "$env:APPDATA\tabby\plugins\node_modules\tabby-smart-upload"
New-Item -ItemType Directory -Force $dst | Out-Null
Copy-Item package.json $dst
Copy-Item -Recurse dist $dst
```

### 验证加载

1. Tabby → 设置 → 插件：列表出现 **Smart Upload / 智能上传** 即加载成功；
   未出现则说明加载报错，看下一步。
2. DevTools：菜单「帮助 → Toggle Developer Tools」（或命令面板搜 Toggle Developer Tools）
   → Console：
   - 成功： `[smart-upload] module loaded`
   - 失败： 红色 `Could not load smart-upload: ...`（把堆栈贴出来排查）
3. 功能冒烟：
   - 新开一个 SSH 会话 → 终端出现一行 `__tsu_cwd(){...};if [ -n "$BASH_VERSION" ]...;__tsu_cwd`
     （注入命令回显，属正常；远端 dotfiles 已配置上报的主机会自动跳过注入）
   - 提示符刷新后 `session.getWorkingDirectory()` 生效：开 SFTP 面板应直接落在当前目录
   - 工具栏出现两个新按钮（上传 / 传输中心）；`Ctrl-Shift-U` 触发上传到当前目录
   - 设置 → 智能上传：配置页可开关各选项

### 常见问题

| 现象 | 排查 |
|---|---|
| 插件列表里没有 | Console 看 `Could not load` 错误；确认 package.json 有 `tabby-plugin` keyword；确认 dist/index.js 存在 |
| 注入后 SFTP 面板仍落在 `/` | 先看终端里注入命令是否回显；`echo $PROMPT_COMMAND`（zsh: `echo $PROMPT_COMMAND`）是否含 `__tsu_cwd`；右键标签页「重试 CWD 目录检测注入」；DevTools 读 `window.__smartUpload.probeAll()` 实测 |
| tmux 里不生效 | tmux ≥3.3 默认关 DCS 透传：tmux.conf 加 `set -g allow-passthrough on` 后重启 tmux |
| 类型报错（npm run build） | npm 版 tabby-* 类型声明滞后于源码是常态；用防御式调用（`(x as any).method?.()`），勿改宿主行为假设 |

## 四、代码结构

```
src/
  index.ts        # NgModule 入口：注册全部 provider，构造函数注入服务使其即时实例化
  config.ts       # ConfigProvider（默认值）+ smartUpload 配置类型（declare module 'tabby-core'）
  i18n.ts         # 轻量 i18n：zh* → 中文，其余英文（宿主 .po 体系不含插件键，键缺失会回显 key）
  icons.ts        # 内联 SVG
  providers.ts    # 工具栏按钮 / 热键 / 标签页右键菜单 / 设置页 四个扩展点
  decorator.ts    # TerminalDecorator：发现 SSH 标签页（鸭式判断 sshSession 属性），调度 CWD 注入
  services/
    cwdInject.service.ts      # 模块A核心：SFTP 静默安装远端钩子（零回显），失败回退终端注入，probe 兜底
    transferCenter.service.ts # 模块B核心：订阅 fileTransferStarted$ 汇聚全部传输，500ms 采样速度/ETA/状态
    upload.service.ts         # 上传到当前目录：解析目标(cwd→记忆→弹窗) → 选文件 → 受限并发 SFTP 上传
  components/
    transferCenterModal.component.ts  # 传输中心模态框（内联模板/样式，ViewEncapsulation.None + su- 前缀）
    uploadPathModal.component.ts      # 目录询问模态框
    settingsTab.component.ts          # 设置页
```

关键设计决策（勿轻易改动）：
- **严禁 service ↔ component 循环依赖**：emitDecoratorMetadata 会让组件的构造器元数据在模块求值期
  引用 Service 类，若 Service 又 import 组件（如 ngbModal.open(组件)），打包后必报
  `ReferenceError: Cannot access 'X' before initialization`（TDZ）。正确姿势：Service 只发
  `openRequested$` Subject，由组件文件里的 `bridgeTransferCenterUi(service, modal)` 桥接，模块构造函数接线。
- **不用 `instanceof SSHTabComponent`**：npm 版 tabby-ssh 类型声明与部分旧版运行时不导出该类；
  用 `'sshSession' in tab` 鸭式判断 + 本地结构化接口（`SSHTabLike`/`ShellSessionLike`）。
- **CWD 自动配置优先静默**：SFTP 读取远端 /etc/passwd 解析 home → 读 ~/.bashrc / ~/.zshrc → 追加受管块（标记 + 备份 + 保留 mode）→ 零回显；SFTP 失败才回退终端注入（紧凑单行，无 base64）。
- **交互式守卫**：片段用 `case $- in *i*)` 包裹——bash 在非交互 ssh 远程命令里也会 source ~/.bashrc，避免 OSC 混入 `ssh host cmd` 输出。
- **拖拽登记判重**：1.0.238 内置 startUploadFromDragEvent 已登记 fileTransferStarted$，插件不得重复 _registerFileTransfer；文件夹选择器不登记 → 用 hasTransfer() 判重后补登。
- **bash hook 用前置拼接** `PROMPT_COMMAND="__tsu_cwd;${PROMPT_COMMAND}"`（不能用尾插，空值/尾分号会产生语法错误）。
- **进度展示不侵入传输机制**：只订阅 `fileTransferStarted$` + 轮询 FileTransfer 状态，内置面板传输自动纳入。
- **拖拽上传**：document 捕获阶段监听 dragover/drop，命中 `div.terminal` 且不在
  `sftp-panel/[dropzone]` 内时接管；通过 `hostView.rootNodes` 把 DOM 反查到具体标签页
  （分屏下拖到哪个 SSH 面板就传到哪个面板的当前目录）；拖拽产生的 HTMLFileUpload 用
  `platform._registerFileTransfer` 手动登记，传输中心才有进度/取消；目录树递归 mkdir + 上传。
- **传输列表顺序**：`TransferCenterService.sortedItems` 按 startedAt 降序（最新在最上）；
  Tabby 自带 transfers 下拉默认「最新在最下」，插件通过 `ApplicationRef.components[0].activeTransfers`
  原地 splice 重排 + `appRef.tick()` 实现最新在前（1.0.238 的 tabby-core 已验证该属性；
  设置项 `reorderBuiltinTransfers` 可关闭；内置结构变化时 try/catch 静默跳过）。
- **点击上传时主动探测 CWD**（`probeCwd`）：钩子只在下次提示符上报，刚连接/钩子失效会误弹路径框；
  点击时发送 `printf '\033]1337;CurrentDir=%s\007' "$PWD"`（Tabby 拦截 OSC 序列不上屏，仅命令行回显），
  150ms 轮询取回。解析顺序：已上报目录 → 主动探测 → 按主机记忆 → 弹窗。
- 上传复用内置 `SFTPSession.upload`（`.tabby-upload` 临时文件 + rename），取消/失败语义与内置一致。
